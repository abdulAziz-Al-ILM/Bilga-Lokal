# Task recurrence and subtasks

Tasks retain their existing rows, IDs, database filename and encryption key. Schema 10 adds `todo_series` and `todo_occurrences`; schema 11 adds `todo_checklist`. Existing task content is not rewritten during these migrations. Portable Tasks content version 9 includes all three tables and imports versions 6–8 with the missing tables treated as empty. The outer encrypted backup format remains unchanged.

A series has one current head. Completing it preserves the old task and occurrence mapping, then creates one successor, its occurrence mapping, checklist and reminder in the same SQL transaction. Unique series/sequence and task/occurrence constraints prevent duplication. Repeating a completion or reopening and re-completing a past occurrence cannot create another current head. A database failure rolls the entire completion back.

Calendar schedules retain their original anchor. January 31 clamps to February's last day and returns to March 31. Weekly schedules use Monday-based calendar weeks with selected weekdays and an interval. Yearly schedules recover leap days. Completion skips missed nominal dates instead of generating a backlog. Local dates follow device wall time; UTC anchors stay UTC. The runtime resolves missing/ambiguous DST clock times; both Dart and Java checks cover New York's gap, overlap and 23/25-hour days. Device timezone changes and reboot remain separate acceptance tests.

Ordinary edits affect the current task only. The explicit future-occurrences switch updates the stored defaults. Changing the schedule reanchors it at the current due date; editing a title with the same schedule retains the original month-end anchor. Historical and completed occurrences cannot change the future schedule through the editor. Trashing or deleting the head stops recurrence. Restoring a trashed task requires explicitly enabling repeat again.

Each task can have up to 200 ordered subtasks, with a title and completion state. These are one-level checklists, without independent dates or reminders. The editor saves title/description, subtask changes, reminder and series-default changes in one transaction. Subtask additions, removals and reordering remain draft edits until Save. Parent completion is an explicit independent action; it does not erase unfinished checklist items. The next recurring occurrence starts with unchecked copies of the series' default titles. A single-occurrence edit does not alter those defaults.

Task duplication creates independent task/checklist IDs, retains ordinary fields and resets completion. It does not inherit recurrence, reminders, attachment ownership or widget disclosure consent. The original task remains unchanged. Task lists display completed/total subtask progress using separate derived metadata, keeping persisted task rows compatible with existing callers.

Subtask titles participate in both task-list search and the task's derived FTS row. Source and checklist triggers update FTS in the same transaction, including native background insertion. Trash removes the parent search result; restoration reconstructs it. Read-only source display and plain-text export include every subtask and its completion state.

Backup validation checks item types, title/count limits, task ownership and unique positions before writing. Import remaps task, series, head, occurrence, checklist and template-folder references together. Repeated imports remain idempotent. Widget permissions remain device-local and excluded from backups; a successor or duplicate never silently inherits disclosure consent.

Native notification completion uses the same series/calendar contract through SQLCipher. A successful commit updates the encrypted native mirror and schedules the successor without waiting for Flutter to open. A crash between SQL commit and mirror publication blocks stale actions until app synchronization; crash-window recovery, process death, reboot and Doze still need broader acceptance. The mirror excludes subtask text and respects existing title/lock/entitlement settings.

## Custom task templates

Schema 12 adds `todo_templates`; portable content 10 includes it and accepts older versions. Versioned payloads contain ordinary task fields and subtask titles, with strict types/limits and no device consent, dates, reminders, recurrence or attachment ownership. Saving from a task is a snapshot. Instantiation rechecks the selected folder and its ancestry and creates task/checklist rows in one transaction. Template revision checks prevent stale updates/deletes. Imported templates receive independent IDs and remain usable after restore. Updating or deleting a template preserves all previously created tasks.
